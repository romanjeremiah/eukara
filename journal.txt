Two issues surfaced after deploying the persona hardening batch.

1. Cloudflare AI schema validation error (5006) on the casual
   Gemma 4 26B route:
     anyOf at '/' not met: required properties at '/audio' are
     'voice,format', ... '/web_search_<truncated>
   Triggered on user message "what can I do about my anxiety"
   which routed default_casual → Gemma 4 with enableGrounding=true.

   Verified against
   https://developers.cloudflare.com/workers-ai/models/gemma-4-26b-a4b-it/
   that the payload shape we send (search_context_size + user_location
   with type/approximate/country/timezone) matches the documented schema.
   So the failure is either:
     (a) Cloudflare deployed a stricter validator that breaks the
         previously-working combination, or
     (b) an undocumented constraint when `tools` + `web_search_options`
         are both set on the same call.

   Hotfix: Gemma removed from supportsGrounding[] in
   src/ai/cloudflare.ts. Casual lane now runs without web_search_options,
   no inline citations on casual replies. Function calling still works.
   Revisit when CF clarifies the schema or we test the no-tools case.

2. NO RECEIPTS rule verbatim leakage:
   User said "I am exhausted", bot replied "You've been carrying this
   for days. Of course you are." — the exact example phrasing from the
   rule. Classic prompt-leakage: the model treated the illustrative
   "if X then say Y" example as a template.

   Hotfix: rewrote the NO RECEIPTS rule in src/config/personas.ts to
   describe the principle without any verbatim example output. Added
   a meta-rule ("do not treat the banned phrases as a template either")
   to head off rephrased copies. The banned-phrases list is retained
   because those are anti-patterns to avoid, not templates to produce.

2026-06-03  Voice-note transcription leak fix
================================================================

User-reported bug: voice notes were getting replies that opened
with a literal 'Transcription: "..."' line followed by the actual
response, all in the same message body.

ROOT CAUSE
  defaultPromptFor() in src/bot/message.ts (line ~767) returned
  'Transcribe this and respond to whatever was said.' as the text
  part of the multimodal user turn when a voice note had no caption.
  Gemini followed the instruction literally — transcribed first,
  then responded — so the transcription appeared in the user-facing
  output stream.

  No separate STT call, no Deepgram. Audio goes directly to Gemini
  multimodal. The 'transcription' was just the model obeying its
  prompt.

FIX (Option A from the discussion)
  Changed the voice/audio default prompt to:
    'Respond naturally to what was said in this audio, as if it
    had been spoken to you in conversation.'
  Drops the transcription request entirely. The model now just
  responds.

  Trade-off: no implicit 'did the bot hear me right' confirmation,
  and conversation history continues to store '[user sent a voice
  note]' as the placeholder rather than the transcribed content.
  Acceptable for speed-of-input use case.

NOT TOUCHED
  - Photo / sticker default ('Describe what you see, and respond
    to it as if I had shared it in conversation.')
  - Video / video_note default ('Watch this and share what stands
    out.')
  - Document default ('Read this and respond to whatever it
    contains.')
  These may have the same leakage pattern (descriptive prose ahead
  of the response) but Roma didn't flag them and the user often
  WANTS a photo description, so the call is less clear-cut.

Deferred follow-up if this becomes a problem: do the same Option A
treatment across all media kinds, or move to Option C (explicit STT
via @cf/deepgram/nova-3 with the transcription as a real artefact
in conversation history). For now, voice is the only path changed.

ROOT CAUSE (verified against Cloudflare docs)
  index.ts wrapped handleMessage in ctx.waitUntil(task). The slow Pro
  Gemini call (grounded, 25 custom tools, thinking) exceeded the 30s
  waitUntil ceiling and was silently cancelled.
  Source: https://developers.cloudflare.com/workers/platform/limits/
  "When the client disconnects, tasks are canceled unless you call
   waitUntil() to extend execution by up to 30 seconds."
  Paid plan does NOT raise this. Paid only changes CPU time cap
  (default 30s, configurable up to 5min). HTTP duration is unlimited
  while client connected.

    provider wired).
  - Timeouts per tier: 90s / 45s / 30s, total worst case 165s, well
