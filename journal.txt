Follow-up to the morning's thought-leakage + architect fixes. Started

ROOT CAUSE (verified against Cloudflare docs)
  index.ts wrapped handleMessage in ctx.waitUntil(task). The slow Pro
  Gemini call (grounded, 25 custom tools, thinking) exceeded the 30s
  waitUntil ceiling and was silently cancelled.
  Source: https://developers.cloudflare.com/workers/platform/limits/
  "When the client disconnects, tasks are canceled unless you call
   waitUntil() to extend execution by up to 30 seconds."
  Paid plan does NOT raise this. Paid only changes CPU time cap
  (default 30s, configurable up to 5min). HTTP duration is unlimited
  while client connected.

ROMA'S DECISIONS (confirmed before implementation)
  - Cascade: Tier 1 gemini-pro-latest, Tier 2 gemini-3.5-flash,
    Tier 3 @cf/google/gemma-4-26b-a4b-it. Matches Xaridotis B2C
    cascade minus OpenAI/Anthropic middle tiers (Eukara has neither
    provider wired).
  - Timeouts per tier: 90s / 45s / 30s, total worst case 165s, well
    within the queue consumer's 15-min budget. Promise.race wrappers,
    not AbortSignal (provider-agnostic, no SDK plumbing).
  - Sticky Pro routing (Option C): KV anchor written after every
    successful Pro turn. Next user message triggers a content-based
    topic shift classifier; same topic -> force Pro, different ->
    clear flag and fall through to normal routing.
  - Dispatch: Pro lane -> queue (15-min wall clock). Casual lane ->
    `await task` inline (HTTP handler stays connected, no 30s cap).
    Callbacks/polls -> ctx.waitUntil (short, no concern).
  - No CPU cap in wrangler.jsonc — default 30s is plenty since calls
    are I/O bound.
  - DO NOT TOUCH mood flow or active-checkin override — separate
    session for emotion category expansion + 24h check expiry.

BUG 1 — medication "yes" reply leaked 715-char planning monologue
  Logs: round 0 textLen=715 + toolCalls=1, round 1 textLen=59 toolCalls=0.
  Cause: tool loop accumulated text across all rounds. Gemma 4 with

  in round 0; the actual reply is in round 1. Concatenation shipped both.
  Pre-existing bug, surfaced by migration of Pro slot away from the
  thought-channel-separated 2.5-pro.
  FIX (Option A, message.ts): only the FINAL no-tool-calls round sets
  fullText. Rounds with toolCalls drop their text entirely.

BUG 2 — mood analysis (score-2 path) leaked persona instruction echo
  Path: src/bot/poll.ts:handlePollAnswer — calls provider.chat() directly
  and pipes output only through normaliseMarkdown, never
  stripLeakedThoughts. Same gap in handleClinicalConcern and
  mood-callbacks.ts:handleEmotionsDone.
  FIX: import stripLeakedThoughts at all three call sites. Apply before
  normaliseMarkdown. Also strengthened stripLeakedThoughts itself with
  a new stripPlanningPreamble() pass using PLANNING_PATTERNS regex
  array — detects prose-form planning paragraphs at the START of the
  response ("The user responded...", "Based on the directive...",
  "Plan:", "I should:", "If I have tool calling..."). Conservative:
  requires at least one non-planning paragraph to remain or returns
  the original.

BUG 3 — /architect stuck on "Step 3/3: Saving and delivering results..."
  Workflow.run logged Ok at 1:48:51 but the message never updated.
  Cause: final editMessageText doesn't check res.ok. fetch() does not
  throw on 4xx; Telegram's 400 (likely HTML parse failure in the
  suggestions blob) silently no-ops while the workflow reports success.
  FIX (architect.ts): await response.json(), check ok flag. On failure
  retry once with parse_mode stripped and HTML tags removed so the user
  still gets the content. Throw on persistent failure so the workflow
  shows as errored rather than silently-stuck.
